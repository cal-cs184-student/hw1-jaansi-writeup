Overview

In this assignment we built a 2D triangle rasterizer that renders vector .svg scenes into a pixel framebuffer. Starting from point and line drawing, we implemented single-color triangle rasterization with edge functions, antialiasing through grid supersampling, hierarchical transforms (the robot task), barycentric interpolation of per-vertex attributes, and finally texture mapping with two axes of sampling control: pixel sampling (nearest vs. bilinear within a texture image) and level sampling (choosing mipmap levels to combat minification aliasing).

A rasterizer is really a machine that point-samples continuous 2D signals (triangle coverage, colors, textures) onto a discrete pixel grid, and every task is about reducing the aliasing that point-sampling introduces:

  • Supersampling attacks aliasing at the coverage/edge level.
  • Bilinear pixel sampling smooths magnified textures.
  • Mipmap level sampling smooths minified textures, using screen-space derivatives to estimate how fast the texture is changing per pixel.

Task 1: Drawing Single-Color Triangles

How we rasterize a triangle

For each triangle we first compute the signed area \[ \text{area} = (x_1-x_0)(y_2-y_0) - (y_1-y_0)(x_2-x_0). \] If it is zero the triangle is degenerate and we skip it. If it is negative the vertices are clockwise, so we swap two of them to guarantee a consistent counter-clockwise winding, which makes the "inside" test the same sign for every triangle.

We then build the three edge functions. For edge \(i\) running from vertex \(i\) to vertex \(j=(i{+}1)\bmod 3\), we precompute coefficients so that \[ E_i(p_x,p_y) = A_i\,p_x + B_i\,p_y + C_i,\qquad A_i = y_i - y_j,\; B_i = x_j - x_i,\; C_i = x_i y_j - x_j y_i. \] \(E_i\) is a signed linear function that is zero exactly on the edge line and positive on the triangle's interior side. A sample point is inside the triangle iff \(E_0, E_1, E_2\) are all \(\ge 0\). We test each sample at its center and fill it if the test passes.

Rather than looping over every pixel in the bounding box, our implementation walks the triangle scanline by scanline. For a fixed sample row with center \(p_y\), each edge inequality \(A_i p_x + (B_i p_y + C_i) \ge 0\) becomes a bound on \(p_x\): edges with \(A_i>0\) give a left bound and edges with \(A_i<0\) give a right bound. Intersecting the three bounds gives the exact horizontal span [lo, hi] of the triangle on that row, and we fill only that span. Vertical edges (\(A_i=0\)) either reject the whole row or impose no horizontal bound.

Why this is no worse than checking the whole bounding box

We initialize the span to the bounding-box columns [Xmin, Xmax] and the constraints can only ever narrow it (each edge does lo = max(lo, ...) or hi = min(hi, ...)), never widen it past the box. So:

  • The span is always a subset of the bounding-box row, so we never touch a sample the bounding-box method wouldn't have.
  • In the absolute worst case (a row completely covered by the triangle, edge to edge) the span equals the full bounding-box row, so we do the same work as the naive method.
  • The per-row setup is \(O(1)\) (just three edge evaluations to compute the bounds), so it adds no asymptotic overhead.

Therefore the algorithm is never slower than the bounding-box scan and is strictly faster on every row that isn't fully covered (which is most of them, especially for thin or slanted triangles).

Extra Credit: scanline-span optimization & timing

The optimization above is exactly the "special optimization beyond simple bounding-box rasterization": instead of testing all three edge functions at every sample in the box, we solve the edge inequalities once per row to jump straight to the covered span. Task 2: Antialiasing by Supersampling

Algorithm and data structures

Supersampling reduces aliasing by taking more than one coverage sample per pixel and averaging them, which approximates each pixel's true fractional coverage instead of a hard in/out decision. Our sample_buffer is a flat array of width × height × sample_rate colors. For a sample rate \(s\) we use an \(n \times n\) grid with \(n = \sqrt{s}\), so each pixel owns \(s\) sub-samples laid out contiguously; the sub-sample at sub-column si, sub-row sj of pixel \((x,y)\) lives at index (y*width + x)*sample_rate + sj*n + si.

The changes to the pipeline were:

  • Rasterization: the scanline loop runs on a grid \(n\) times finer in both axes. Each sub-sample's center is \(\big(\frac{X+0.5}{n}, y+\frac{sj+0.5}{n}\big)\) and passes the same three edge-function test; passing sub-samples are written into their slot in sample_buffer.
  • Buffer sizing: set_sample_rate and set_framebuffer_target resize sample_buffer to include the sample_rate factor.
  • Resolve: resolve_to_framebuffer box-averages the \(s\) sub-samples of each pixel down to one final RGB color (clamped and written to the display buffer).
  • Points/lines: fill_pixel writes the same color to all \(s\) sub-samples of a pixel, so non-triangle primitives still resolve correctly (they don't need true coverage supersampling).

This antialiases triangle edges because a pixel straddling an edge now has some sub-samples inside and some outside; averaging produces an intermediate color proportional to how much of the pixel the triangle covers, turning a hard jagged step into a smooth gradient.

At rate 1 the thin corner breaks up: each pixel is either fully colored or fully empty depending on whether its single center sample happens to fall inside the sliver, so the corner looks jagged and pieces of it drop out entirely. As the rate rises to 4 and 16, the extra sub-samples recover partial coverage: edge pixels take on graduated shades and the corner reads as a smooth, continuous taper. This is exactly the expected result: more samples give a better estimate of the true coverage integral over each pixel.

Task 3: Transforms

For my_robot.svg we posed cubeman as a friendly waving robot named Tillu, recolored red. The pose is built entirely from nested transform groups:

  • Head: cocked to one side with a rotate(45) for personality. The face (two eyes and a smile made from a bar with raised corners) is placed outside the head's rotation group so it stays upright and readable even though the head block is tilted.
  • Right arm: raised at the shoulder (rotate(-45)) and then bent again at the elbow in a second nested group so the forearm points up in a waving gesture.
  • Left arm: rotated -75° at the shoulder so it hangs naturally down by his side.
  • Legs/torso: scaled and translated cube primitives forming the body.

The point we were exploring is how hierarchical (parent-child) transforms compose: rotating a shoulder group automatically carries the elbow and hand with it, so a natural wave is just two rotations stacked, while deliberately keeping the face out of the head's rotation group shows the flip side: in this case we didn't want the face to inherit the head's rotation.

Task 4: Barycentric coordinates

Barycentric coordinates express any point \(P\) inside a triangle as a weighted average of its three vertices, \[ P = \alpha V_0 + \beta V_1 + \gamma V_2, \qquad \alpha + \beta + \gamma = 1, \] where each weight is the fraction of the total area contributed by the sub-triangle opposite that vertex. A vertex has weight 1 at itself and 0 along the opposite edge, and the weights vary linearly in between. This makes them perfect for interpolating any per-vertex attribute (here, color): a point takes \(\alpha\) of \(V_0\)'s color plus \(\beta\) of \(V_1\)'s plus \(\gamma\) of \(V_2\)'s, so three pure red, green, and blue vertices produce a smoothly blended color field.

In code we reuse the edge functions from Task 1: the same \(E_i\) that test coverage are, once divided by the triangle area, exactly the barycentric weights. Per sample we compute \(\alpha = E_1/\text{area}\), \(\beta = E_2/\text{area}\), \(\gamma = 1-\alpha-\beta\), and write \(\alpha c_0 + \beta c_1 + \gamma c_2\) into the sample buffer.

Task 5: "Pixel sampling" for texture mapping

Pixel sampling is how we read a color out of a texture image once we know a point's texture coordinates \((u,v)\). In rasterize_textured_triangle we barycentrically interpolate the per-vertex UVs to get \((u,v)\) at each sample, scale by the texture dimensions to land in texel space, and then fetch a color one of two ways:

  • Nearest (sample_nearest): round to the single closest texel and return it. Cheap, but blocky, since neighboring pixels that map near a texel boundary snap to different texels.
  • Bilinear (sample_bilinear): take the 4 texels surrounding the sample and blend them by the fractional position \((s,t)\) within that texel cell, \(\text{lerp}\big(\text{lerp}(T_{00},T_{10},s),\,\text{lerp}(T_{01},T_{11},s),\,t\big)\). Slightly more work, but continuous, so it removes the blockiness.

The difference is largest when a single screen pixel maps to roughly one texel or to a region with high-frequency detail, e.g. thin lines or sharp color boundaries in the texture, and especially under minification with a low sample rate. There, nearest sampling shows hard steps and sparkle because tiny changes in \((u,v)\) flip which texel is chosen, while bilinear averages across the transition and stays smooth. When the texture is over-sampled (magnified so many pixels share a texel, or the sample rate is high enough to already average things out) the two methods converge and the difference shrinks.

Task 6: "Level Sampling" with mipmaps for texture mapping

Level sampling fixes the minification problem: when a surface is far away, one screen pixel covers many texels, and sampling just one of them (even bilinearly) misses all the others and aliases. A mipmap precomputes a pyramid of the texture at successively halved resolutions, where each higher level is an already-averaged version of the one below. Level sampling picks the level whose texels are about the size of one screen pixel, so a single lookup already represents the whole footprint.

Choosing the level

The right level depends on how fast \((u,v)\) changes per screen pixel. In rasterize_textured_triangle we compute, for each sample, the UV at the neighboring pixels \((x{+}1,y)\) and \((x,y{+}1)\) and store them in the SampleParams (this is cheap because UV is affine in screen space, so the per-pixel deltas are constant across the triangle). In Texture::get_level we difference them to get \(\big(\frac{du}{dx},\frac{dv}{dx}\big)\) and \(\big(\frac{du}{dy},\frac{dv}{dy}\big)\), scale by the full-resolution texture size to get texel-space lengths, and take \[ L = \log_2\Big(\max\big(\|(\frac{du}{dx},\frac{dv}{dx})\|,\; \|(\frac{du}{dy},\frac{dv}{dy})\|\big)\Big). \] This \(L\) is exactly "how many texels wide is one pixel's footprint, in powers of two." Then Texture::sample uses the level-sampling mode:

  • L_ZERO: always sample level 0 (full resolution): Task 5 behavior, aliases under minification.
  • L_NEAREST: round \(L\) to the nearest integer level and sample that one.
  • L_LINEAR: sample the two levels bracketing \(L\) and linearly blend them by the fractional part. Combined with bilinear pixel sampling this is full trilinear filtering.

We verified the level computation with a debug mode (D key) that renders \(L\) as grayscale: zooming out brightens the image (higher levels as the footprint grows) and zooming in darkens it toward black (level 0), confirming the derivatives and \(\log_2\) are correct.

Speed / memory / antialiasing trade-offs

TechniqueSpeedMemoryAntialiasing power
Supersampling (raise samples/pixel) Slowest: cost scales linearly with the sample rate Highest: sample buffer grows \(s\times\) General: fixes edge aliasing and texture aliasing, but expensive
Pixel sampling (nearest → bilinear) Fast: bilinear is ~4 texel reads + a blend None extra Helps magnification / smooths within a level; does nothing for minification
Level sampling (mipmaps) Fast: 1 lookup (nearest) or 2 (trilinear) regardless of minification +~33% for the whole pyramid (one-time) Specifically targets minification aliasing very cheaply

tldr: supersampling is the brute-force hammer: the most powerful option, but the most expensive in both time and memory. Mipmapping trades a fixed one-third of extra memory for very cheap, minification-specific antialiasing that stays constant-cost no matter how far away the surface is. Bilinear pixel sampling is nearly free and helps magnification but can't help minification on its own. The three are complementary and combine (e.g. trilinear + a modest sample rate).

Four sampling combinations

Our texture is a detailed animated-film frame (lots of fine foreground debris and background detail), placed in img/ and mapped by a copy of svg/texmap/test5.svg whose <texture> filename points at it (svg/texmap/kungfupanda.svg). We zoomed out so the texture is minified, which is where level sampling matters. Going from L_ZERO to L_NEAREST removes the minification sparkle in the fine detail; adding P_LINEAR further smooths within each level. The differences are clearest in the pixel inspector, where L_ZERO shows sharp high-contrast texels and the mip-mapped modes show smoother, averaged ones.

Extra Credit: Anisotropic filtering

Trilinear filtering picks one level from the longer footprint axis, so a footprint that is long and thin (a surface seen at a grazing angle) gets over-blurred across its short axis. Anisotropic filtering instead treats the pixel footprint as an ellipse: it takes several samples stepping along the major (long) axis and chooses the mip level from the minor (short) axis, so detail is preserved along the thin direction. We implemented it as a fourth level mode (L_ANISOTROPIC, alongside L_ZERO, L_NEAREST and L_LINEAR):

  • Reuse the two footprint vectors from get_level; the longer one gives the step direction and sample count \(n = \lceil \text{major}/\text{minor} \rceil\) (capped at 16), the shorter one gives the level \(L = \log_2(\text{minor})\).
  • Take \(n\) trilinear samples spread along the major axis, centered on the sample's UV, and average them.

Because it takes up to 16 trilinear samples per pixel, it is markedly slower, which the clock() timings (printed each frame from DrawRend::redraw()) confirm. Measured on svg/texmap/test5.svg (Berkeley seal), nearest-pixel mode:
